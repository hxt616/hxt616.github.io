Python 多进程：fork、spawn 与 main

发表于 2026-06-09 分类于 Python
本文字数： 2.8k 阅读时长 ≈ 3 分钟

在 Python 中进行多进程（multiprocessing）开发时，很多人经常会被跨平台报错、死锁或者莫名的无限递归卡住。要彻底解决这些问题，我们需要理清三个核心概念：进程启动方式、上下文（Context）以及为什么必须加 if __name__ == '__main__':。

一、 进程创建流程（Fork vs Spawn）

Python 启动一个新进程主要有两种底层机制，它们的区别决定了代码的安全性和执行效率。

1. Fork

  • 怎么工作：这是 Linux/Unix 系统的默认方式。它就像是“克隆”，当主进程要开新进程时，操作系统把主进程现有的内存、变量、打开的文件等原封不动地复制一份给子进程。
  • 优缺点：因为不需要重新加载代码，它的启动速度极快。但是，它有一个致命隐患——死锁。如果主进程里有很多线程，fork 时某个后台线程刚好给某个资源上了锁，子进程会把这个“锁死”的状态一起复制过去。但负责开锁的线程在子进程里不存在，子进程一旦访问这个资源，就会永久卡死。

2. Spawn

  • 怎么工作：这是 Windows 和 macOS 的默认方式。它不搞克隆，而是白手起家。主进程会启动一个完全干净、全新的 Python 解释器。子进程为了知道自己要干什么，必须把你的 Python 脚本重新读取（import）一遍才能获取要执行的函数，并且只能通过序列化（Pickle）接收主进程传过来的核心数据。
  • 优缺点：因为要重新加载环境和代码，启动速度比 fork 慢。但它极其安全，进程之间完全隔离，彻底避免了死锁问题。

行业趋势：由于 fork 的安全性隐患，现代 Python（包括 macOS 和未来的 Linux 版本）都在默认或者全面转向更安全的 spawn。

产生错误的过程：

  1. 主进程启动：直接运行脚本，此时 __name__ 的值是 __main__。代码向下跑，执行到 process.start()。主进程通过 spawn 方式告诉系统：“帮我开一个全新的子进程。”
  2. 子进程诞生：子进程是一个完全空白的 Python 解释器。它在脑子里找不到你要运行的那个函数。为了把函数加载到内存里，子进程必须把你的这个脚本从头到尾重新导入（import）一遍。
  3. 连环爆炸：子进程在重新读取脚本时，因为没有 if __name__ == '__main__': 的拦截，它会老老实实地把脚本里的代码再执行一遍。当它执行到 process.start() 时，子进程也会向系统申请：“帮我再开一个全新的孙子进程。”
  4. 无限循环：孙子进程启动，为了加载函数，又重新导入脚本，又创建重孙进程……在几毫秒内，系统会陷入无限递归创建进程的死循环，直到系统崩溃。

防止错误

当你加上 if __name__ == '__main__': 之后：

  1. 主进程满足条件，成功创建子进程。
  2. 子进程为了加载函数，重新导入（import）脚本。
  3. 导入时，子进程内部的 __name__ 变量变成了当前的文件名，不再是 __main__。
  4. 于是子进程卡在 if 判断外面，创建新进程的代码被完美拦截。子进程顺利加载完函数，高高兴兴去干活了。

Warp

SM中包含多个Warp：

  • 每个Warp（线程束调度器）可以调度32个线程，对应SIMT（单指令，多线程）
  • 也就是说，所有的 Thread 以锁步的方式执行同一条指令，但是每个Thread通过自己的唯一ID（threadIdx）处理数据中的不同部分

当程序员定义了一个包含N个Thread的Block时，GPU硬件会自动将Block内的Thread按顺序每32个组成一个Warp。

因此写代码时一般建议将Block的Thread总数设置为32的整数倍，避免Warp资源浪费。

  • Warp 固定 = 32 线程
  • Block 最大 = 32 Warp（1024 线程）
  • SM 最大 Warp 数 = 64（现代 GPU）
  • SM 可以同时运行来自不同 Block 的多个 Warp，也可能不会同时执行

指令加载流程

让我们追踪一个简单的 FADD (浮点加法) 指令，它来自某个 Warp 中的一个线程。

  1. L2 缓存 (L2 Cache)：指令数据最初在显存 (VRAM) 中。在执行前，包含 FADD 指令的代码块被从显存加载到 L2 缓存。L2 缓存是所有 SM 共享的“大仓库”。

    当GPU核心需要数据时，首先在L2缓存中查找。如果命中（hit），就直接从L2返回，避免了访问慢速的HBM。如果未命中（miss），才去HBM（主存）中读取，同时将这个数据块加载到L2中，供后续访问使用。

  2. L0 指令缓存 (L0 ICache)：当 SM 准备执行这个 Warp 时，它会从 L2 缓存中将所需的指令块取到自己专属的 L0 指令缓存中。你可以把 L0 ICache 看作是 SM 私有的“指令小仓库”，比 L2 快得多。

  3. Instruction Fetch (指令获取单元)：这是 SM 内部一个专门负责“取指”的单元。每个时钟周期，它会根据 Warp Scheduler 的指令地址，从 L0 指令缓存中取出下一条要执行的指令。这里要区分一下：

    • L0 ICache：存储指令的地方，像一个仓库。
    • Instruction Fetch：读取指令的单元，像一个搬运工。

  4. Warp Scheduler (线程束调度器)：Instruction Fetch 取回的指令被交给 Warp Scheduler。Warp Scheduler 内部维护着大量 Warp 的状态（已就绪、阻塞等）。当它发现一个 Warp 的指令已经取回且操作数就绪时，它就会在下一个周期选择这个 Warp。

  5. Dispatch Unit (分派单元)：Warp Scheduler 选中某个 Warp 后，会将取回的指令（如 FADD R1, R2, R3）发送给 Dispatch Unit。Dispatch Unit 负责解码这条指令，确定其类型（是浮点运算？是内存访问？），并将其派发（发送）到正确的执行单元队列中。在我们的例子中，它会被派发给 FP32 CUDA Core。

  6. 执行单元：最后，FP32 CUDA Core 从自己的队列中拿到这条指令，读取源寄存器 R2 和 R3 的值，执行加法，并将结果写回目标寄存器 R1。至此，这条指令执行完毕。

  3. 查找L2缓存：请求继续传到统一的L2缓存（40MB）。如果L2命中，直接跳到步骤5。
  4. 访问HBM：L2未命中 → L2控制器向HBM内存控制器发出请求 → HBM从物理显存颗粒中读取包含目标地址的128字节缓存行 → 数据通过HBM接口传回L2缓存。
  5. 数据返回L1/SHM：L2将数据返回给L1/Shared Memory。
  6. LDST单元收集数据：LDST单元从L1中取出需要的4字节（一个float），然后将其写入CUDA Core的寄存器R1。
  7. 执行完成：Warp Scheduler收到LDST单元的信号，标记该加载指令已完成，现在Warp中等待这个数据的线程被解除阻塞

CUDA与GPU物理架构映射

映射关系

CUDA 编程概念 (逻辑) GPU 硬件概念 (物理) 核心关系
Thread (线程) CUDA Core (CUDA核心) 执行于其上
Thread Block (线程块/CTA) Streaming Multiprocessor (SM) 由一个SM完整执行
Grid (网格) Device (设备/GPU) 在一个设备上执行
  1. CUDA核心 → 线程 (Thread)：线程是执行的最小单位，而CUDA核心是真正执行线程运算的物理单元。一个线程在某个时刻就是在一个CUDA核心上执行。
  2. 多核处理器 (SM) → 线程块 (Thread Block)：线程块中的线程会被分配到同一个SM上，并且可以共享SM内的共享内存和同步。同一个线程块内的所有线程，一定在同一个SM上同时（或分时）执行。但一个 SM 可以有多个 Block（只要资源足够）。
  3. 设备端 (Device) → 线程块组合体 (Grid)：Grid对应整个GPU设备，它是一个完整的任务（kernel）。所有SM一起协作，完成一个Grid中所有线程块的工作。一个Kernel函数唯一对应一个Grid，所有属于同一Grid的Block，都执行同一个Kernel函数，共同处理同一个计算任务。

约束

  1. Block不宜过小：一个Block需要占用SM的资源（共享内存、寄存器）。如果块太小，一个SM里要分时处理很多块，调度开销会比较大。
  2. Block不宜过大：如果一个Block的线程数太多，它需要的计算和存储资源就会超过单个SM的最大容量，导致这个Block没法放到任何SM上去执行。
  3. Block内资源共享：Block内的线程通过SM内的共享内存进行低延迟通信，并通过 __syncthreads() 进行同步。
  4. Block间无直接交互：不同Block之间无法直接共享内存或同步，它们只能通过全局内存来交换数据。

使用shared memory的情况

  1. 数据会被同一个 Block 内的多个线程重复读取

    这是最经典、收益最高的场景。

    • 例子：矩阵乘法、卷积、滤波。一个数据（如图像的一个像素）会被同一个 Block 里的几十个线程反复用到。
    • 效果：从全局内存读一次（~400 周期），然后让 32 个线程从共享内存读（~30 周期）。这能减少 90% 以上的全局内存访问。

  2. 同一个 Block 内的线程之间需要交换数据或协作

    共享内存是 Block 内所有线程的“公共黑板”。

    • 例子：并行规约（求和、找最大值）、排序、直方图计算。线程 A 把中间结果写在共享内存上，线程 B 可以直接看到并用它来计算。
    • 效果：没有共享内存，线程间通信只能通过全局内存（慢）或原子操作（更慢）。共享内存让协作变得可行且高效。

  3. 需要合并对全局内存的“不规则”访问

    共享内存可以作为“重新排布数据”的缓冲区。

    • 例子：矩阵转置。每个线程从全局内存读一个数，但写出去时，位置是“乱”的，导致写入全局内存的效率很低。
    • 技巧：先把数据读到共享内存里排好队（无成本），然后再以“合并访问”的方式整齐地写回全局内存。用共享内存的“慢”换全局内存的“快”。

Stream

流 是 GPU 上的一条命令队列，是主机端（CPU）向设备端（GPU）提交一系列操作（如内核启动、cudaMemcpyAsync）的任务队列。核心作用是让你能从 CPU 端将不同的任务（例如，在流1中拷贝数据，在流2中运行内核）并发地提交给 GPU 去执。

stream 和cp.async的异步不同：

  1. Stream 管理的是“粗粒度”并发：控制着主机端发起的、独立的大任务（如整个内核或大的数据拷贝）如何在 GPU 上排队和执行。
  2. cp.async 实现的是“细粒度”并发：在一个内核内部，控制着加载数据（全局→共享）和计算数据（使用 Tensor Core）这两个步骤如何流水线化地重叠执行
  • 同一个流里的操作（内核启动、内存拷贝）严格按照先后顺序执行。
  • 不同流里的操作，在硬件允许的情况下可以同时执行（并发）。
  • 不用流时（默认情况），所有操作都在默认流里排队，GPU 一次只做一件事，CPU 还得干等着（同步），这叫阻塞式。

内存事务 Memory Transaction

GPU 内存事务是指 GPU 执行一次内存访问操作（读或写）时，从显存到 SM（流式多处理器）之间传输数据的基本单元。它和 CPU 内存访问不同，具有合并访问、对齐要求、广播特性等特点。

GPU 的显存访问不是按单个字节或 4 字节进行的，而是按事务（Transaction）进行的。一次事务传输 32 字节（在 NVIDIA GPU 中称为 sector）或 128 字节（cache line）。

对于一次 cache line 的数据传输有不同的形式：

  • 32 threads（一个warp） * 4 Bytes
  • 每个线程一次最多可以加载16字节，128 Bytes = 16 Bytes * 8 threads

如果线程访问地址不连续、不对齐，会导致大量额外事务，严重降低性能。

合并访问

合并访问是指一个 warp（32 个线程）的内存访问能够被合并成尽可能少的内存事务。

coalescing（合并） 只解决：“多个线程之间”的访存合并

理想情况：完美合并

非合并情况：完全发散

虽然warp中的线程仍然是同时执行的（warp lockstep），但是访存事务会分为很多个，效率下降

当 GPU 线程在等待数据从显存加载到寄存器时，GPU 硬件调度器（Warp Scheduler）会立即切换到另一个准备好的 Warp 执行计算，从而让计算单元（CUDA Core）始终忙碌，不让它因“等数据”而空闲。

  1. Warp 0：发起加载A[i]，B[i] → 进入等待。
  2. Warp 0 被挂起，Warp 调度器立即切换到 Warp 1，加载其数据。
  3. Warp 1 等待，调度器切换至 Warp 2，以此类推。
  4. Warp 3 同样开始等待。
  5. 此时，之前某次加载可能已完成，调度器会切换回准备好的 Warp 0 进行计算和存储，然后继续下一轮迭代。
  6. 如此循环往复，CUDA核心几乎始终在执行计算，处于繁忙状态。

  • 定位：现代层次化布局与张量引擎抽象库。

  • 特点：非常底层且抽象，是当前编写新一代（如 Hopper/Blackwell 架构）极致性能算子的核心工具。

Thrust

  • 定位：高层并行算法库（类似 C++ STL）。
  • 解释：这是一个高级的并行通用算法库，其接口设计极度模仿了 C++ 标准模板库（STL）。它提供了诸如 thrust::sort、thrust::reduce、thrust::transform 等高维抽象接口。

三个核心类

1. Layout（布局）= Shape + Stride

这是 CuTe 的灵魂。Layout 决定了逻辑上的矩阵坐标（比如第 i 行第 j 列）如何映射到一维的物理内存地址。

  • Shape：矩阵的几何形状（如 8行 8列）。
  • Stride：步长，即在某一个维度移动 1 步，物理地址跳过多少个元素。也就是可以确定是列优先还是行优先

无论在数学上或者在代码里你的矩阵是二维（\(M \times N\)）、三维甚至更高维，在物理硬件层面上，GPU 的显存（Global Memory / HBM）只有一维的线性地址空间。 显存里的每一个存储单元都是按地址顺序 0x00, 0x01, 0x02... 排开的。

所以不论是列优先还是行优先，影响的只是计算物理地址的结果：物理偏移 = r * 行步长 + c * 列步长

注意：CuTe 强烈推荐使用静态整型（如 Int<8>{}），因为只有编译期常量才能让编译器进行彻底的乘法和地址优化。

2. Tensor（张量）= Engine + Layout

Tensor 是包含了具体数据指针和 Layout 的实体。

  • 你可以用它定义全局显存（Global Memory）的数据、共享内存（Shared Memory）的 数据，或者寄存器（Register）的数据。

Engine 是数据源的抽象（类似于 C++ 中的迭代器，可用于定位数据），主要负责：

  1. 数据类型的迭代器/指针（它是通过指针访问，还是通过数组访问？）。
  2. 数据的生命周期与存储位置。

三种 Engine：

① ArrayEngine（寄存器存储）

  • 位置：GPU 寄存器（Registers）。
  • 特点：大小在编译期就完全确定，通常用来存放线程私有的局部数据（如 Tensor Core 矩阵乘法的中间累加结果）。
  • 对应：类似于 std::array<T, N>。

② ViewEngine（引用/指针存储）

  • 位置：全局显存（Global Memory）或共享内存（Shared Memory）。
  • 特点：它自己不拥有数据，只是一个指针的包装。它指向别处已经开辟好的内存。
  • 对应：类似于 C 语言中的裸指针 T* 加上一些边界检查。

③ OwningEngine（拥有所有权的存储）

  • 位置：通常用于动态分配或特定的静态共享内存。
  • 特点：自己负责内存的申请和释放。

3. Tiling & Slicing（分块与切片）

FlashAttention 的核心是分块（Tiling）。在 CuTe 中，你可以直接用一个 Layout 去切另一个 Tensor，不需要手写循环索引。这里不发生数据传输

向量变换完整流程

1. 基本概念

  • 输入序列 (input_ids): [a, b, c, ...]，长度为 T，batch size 为 B

  • 隐藏状态 (hidden_states): [B, T, H]

  • logits: [B, T, V]，每个位置预测下一个 token

    logits: [B, T, V]，其中 V 是词表大小。对于每个seq来说，最后都会计算出一个长度为 V 的 logits 向量，而该维度（V）上的每个数值表示模型认为该 token 作为下一个输出的不同分数（或置信度），所以每次 forward 计算的 logits，就是下一个 token 的所有可能值组成的向量。

  • KV cache: 每一层的 Key/Value，用于推理阶段避免重复计算

  • Causal mask: 下三角矩阵，保证每个 token 只看当前及之前 token

2. logits 与 token 的对应关系

hidden_state/logits 位置 对应预测 token
logits[:, i, :] input_ids[i+1]
  • 训练阶段: logit[:, i, :] 对应的 label 是下一个 token
  • Prefill 阶段: logit[:, -1, :] 对应最后一个 token 的下一个 token，用于生成
  • Decode / 推理阶段: logit[:, 0, :] 对应当前新 token 的下一个 token

3. 训练 vs 推理阶段 attention 的区别

训练阶段（teacher forcing）

  • 输入完整序列 [a, b, c, d]

  • Q/K/V 全部计算 [B, T, H]

  • attention mask: 下三角矩阵，保证因果性

  • 计算一次 forward 即可，logits [B, T, V]

  • KV cache 不需要，历史 token 重复计算没问题

  • 每个 token 的 Q 与该位置及之前的 K 进行 attention

推理阶段（逐 token decode）

  • Prefill 阶段: 与训练一致，都需要mask，计算完整上下文，生成每层 KV cache

  • Decode 阶段:

    • 输入仅新 token [e]

    • Q 只有新 token

    • K/V = concat(历史 KV + 新 token KV)

    • attention 只计算 新 token的 Q 与所有 K 的 attention

    • causal mask 仍存在，但只有 1 行，实际不起作用

    • logits 只对应 1 个 token

4. KV cache 的作用

  • 训练阶段: 不需要 KV cache
  • 推理阶段:
    • 每一层的 K、V 都需要保存
    • 每层每个时间步的 KV 只服务于同一层的未来 token
    • 上一层 KV 不会覆盖上一时间步的 KV

5. logits shape 总结

阶段 input_ids logits shape 对应预测 token
训练 [a,b,c,d] [B, 4, V] [b,c,d,e]
prefill [a,b,c,d] [B, 4, V] [b,c,d,e]，只取最后一个生成 token
decode [e] [B, 1, V] [f]

MHA/MQA/GQA

发表于 2026-01-07 更新于 2026-05-24 分类于 大模型
本文字数： 2.3k 阅读时长 ≈ 2 分钟

在大型语言模型的推理部署中，KV缓存（Key-Value Cache） 是内存消耗的主要来源。为了优化这一瓶颈，业界经历了从多头注意力（MHA） 到分组查询注意力（GQA） 再到多查询注意力（MQA） 的技术演进。目前 GQA 在主流大模型中更为常用，兼具性能与效率优势。

在标准的Transformer架构中，每个输入token会生成三组向量：

  • Q（Query）：查询向量，决定“关注什么”
  • K（Key）：键向量，提供“被比较的内容”
  • V（Value）：值向量，提供“被提取的信息”

多头注意力（MHA）

MHA的核心特点是：每个注意力头都有自己独立的Q、K、V投影矩阵。这意味着： - 若有32个注意力头，就需要32套不同的K/V投影 - 每个token在每个头上都会产生不同的K/V向量 - 每个头的Q只与该头自己的K/V进行计算

这种设计虽然表达能力最强，但KV缓存开销巨大。对于h个头、d维度的模型，处理长度为L的序列时，KV缓存需要存储2×h×d×L个参数。

多查询注意力（MQA）

MQA是GQA的极端形式：所有Q头共享同一套K/V投影。

关键在于：注意力机制的多样性主要来自Q，而非K/V。

虽然所有Q头看到相同的K和V，但：

  • 每个Q头有不同的查询向量
  • 相同的K与不同的Q计算会产生不同的注意力分数
  • 相同的V用不同的权重组合会产生不同的输出

类比理解：多个分析师使用同一份数据集（K/V），但带着不同的问题（Q）进行分析，最终得到不同的报告。

分组查询注意力（GQA）

研究发现，不同注意力头学习的关注模式存在高度相关性。例如： - 某些头专门关注语法结构 - 某些头专门关注语义相似性
- 某些头专门关注位置关系

这些相关头所需的K/V信息存在大量重叠。GQA基于这一洞察，提出了分组共享的策略。

PPO

近端策略优化，其实就是利用奖励模型的结果更新策略模型参数，既希望语言模型的输出能够尽可能地获得奖励模型的高评价，又不希望语言模型的变化过于“激进”

策略 →（生成）→ 响应 →（输入）→ 奖励模型 →（输出）→ 奖励 →（反馈）→ 策略

概述

在大语言模型（LLM）的强化学习微调（RLHF）中，PPO（近端策略优化）是目前的事实标准。它的核心任务非常明确：利用奖励模型（Reward Model）的反馈，指导策略模型（Actor）生成更符合人类偏好的文本，同时利用价值模型（Critic）来评估生成的质量。

为了让你的读者清晰地理解 PPO，我们将它拆解为以下四个核心步骤。

1. 核心思想：在“探索”与“稳定”之间走钢丝

PPO 的核心逻辑可以用一句话概括：既要让模型根据奖励信号变得更好，又不能让它变得太激进，以免破坏原本学好的语言能力。

为了实现这一点，PPO 引入了裁剪（Clipping）机制。它不会无脑地让模型去追求高分，而是限制模型参数更新的幅度。如果某个生成策略带来的优势（Advantage）过高，PPO 会“剪掉”这部分过高的收益，强迫模型保持克制。

2. 四大核心组件

在 PPO 训练流程中，通常有四个关键的“角色”协同工作：

组件 角色定位 核心职责 是否更新
Actor (策略模型) 演员 负责生成文本（回答）。它是训练的主角，参数会不断优化。 ✅ 是
Critic (价值模型) 预言家 评估 Actor 当前的状态值多少钱（预测未来回报 \(V(s)\)）。 ✅ 是
Reward Model 裁判 根据人类偏好数据训练，给 Actor 生成的完整回答打分。 ❌ 否 (冻结)
Reference Model 守门员 通常是 SFT 后的初始模型，用来计算 KL 散度，防止 Actor 变得太离谱。 ❌ 否 (冻结)

3. 训练流水线：从生成到更新

PPO 的训练过程是一个循环的流水线，我们可以将其分为三个阶段：

阶段一：Rollout (采样与打分) 1. 生成：Actor 模型接收提示词（Prompt），生成一段回答（Response）。 2. 计算 KL 惩罚：计算 Actor 生成的每个 Token 的概率，与 Reference Model 的差异（KL 散度）。这是一个负向奖励，用来约束模型不要偏离常识太远。 3. 最终打分：将生成的完整句子交给 Reward Model，得到一个标量分数（RM Score）。 4. 计算即时奖励：将 RM Score 与 KL 惩罚结合，得到最终的奖励值 \(r_t\)。

阶段二：GAE (计算优势与回报) 这是 PPO 中最容易混淆的部分。我们需要计算两个关键指标： * Advantage (优势) \(A_t\)：表示“这一步做得比平均水平好多少”。 * 我们使用 GAE (广义优势估计) 算法来计算。它结合了蒙特卡洛（MC）的准确性和时序差分（TD）的高效性。 * 公式逻辑：\(A_t = \delta_t + (\gamma \lambda) \delta_{t+1} + \dots\) （其中 \(\delta\) 是 TD Error）。 * Returns (回报) \(G_t\)：表示“从这一步开始，未来能拿到的总分”。 * 它是 Critic 模型训练的“标准答案”。 * 计算公式：\(G_t = A_t + V(s_t)\)。

阶段三：Loss 更新 (策略与价值) 利用计算出的 \(A_t\) 和 \(G_t\)，分别更新 Actor 和 Critic： 1. 更新 Critic：计算预测值 \(V(s_t)\) 与目标值 \(G_t\) 的均方误差（MSE），让“预言家”说得越来越准。 2. 更新 Actor：计算 PPO 的裁剪损失（Clipped Surrogate Loss）。 * 计算新旧策略的概率比 \(r_t(\theta)\)。 * 通过 \(\min(r_t \hat{A}_t, \text{clip}(r_t, 1-\epsilon, 1+\epsilon)\hat{A}_t)\) 来确定最终的梯度方向。

特性 奖励模型 价值函数
是什么 一个函数 R(s, a, s')，表示在状态 s 采取动作 a 到达状态 s’ 后，立即获得的反馈信号。 一个函数 V(s) 或 Q(s, a)，表示从当前状态（或状态-动作对）出发，所能获得的长期、累积回报的期望。
时间视角 短视的、瞬时的。只关心“这一步”的直接结果。 远见的、长期的。关心“从今往后”的所有可能结果。
核心问题 “这个动作现在有多好？” “处于这个状态/采取这个动作，未来能有多好？”
人类类比 感官愉悦/痛苦：吃糖的甜味（+奖励），摸火炉的灼痛（-奖励）。 战略判断：选择读大学（现在辛苦，但长期价值高），选择打游戏（现在快乐，但可能损害长期价值）。
在RL中的角色 环境的反馈机制，定义了任务的终极目标。是价值函数计算的原始输入。 智能体的内部认知模型，是进行决策和规划的核心依据。

更新价值模型参数的过程：

  1. 计算 GAE：算法先通过 GAE 公式，结合奖励和 Critic 的旧预测，算出每一步的 Advantage（给 Actor 用来更新策略）。
  2. 推导 Gt (Returns)：然后，把算出来的 Advantage 加上 Critic 的 旧预测值 (values)，反推出 Returns（即 Gt）。
  3. 计算 Critic Loss：最后，用这个推导出的 Returns ( Gt ) 作为标准答案，去训练 Critic，让它的预测越来越准。critic_loss = (G_t - values)²

returns 的计算方式：

  • Advantage (GAE) = 真实的累计回报 ( Gt ) - 旧的预测值 ( Vt)
  • 真实的累计回报 ( Gt ) = Advantage (GAE) + 旧的预测值 ( Vt)

广义优势估计 (GAE)

它定义了在状态 st（提示 + 到目前为止生成的词）下，特定动作 at（词）相对于策略将采取的平均动作的优越程度

两种计算优势的方法：

  • 蒙特卡洛 (MC)：使用完整轨迹的奖励，高方差低偏差
  • 时序差分 (TD)：每一步都会得到一个即时奖励，低方差高偏差

GAE 的目标就是：在这两者之间取得一个可调节的平衡。通过指数加权平均多个 n-step TD（多步TD） 误差，构造一个偏差与方差可控的优势估计量。

为什么使用GAE而不是用真实的奖励来表示

1. 本质定义的区别

  • Gt（真实的折扣回报）：是“真实的未来”。它代表从当前时刻 t 开始，把未来每一步真实发生的即时奖励（rewards）全部打折并累加起来的总和。
    • 公式： Gt=rt+γrt+1+γ2rt+2+…
  • rewards[t] + gamma * values[t+1]（TD Target）：是“一步真实 + 一步预测”。它只拿了当前这一步的真实奖励 rewards[t]，然后对于未来的部分，它没有去一步步累加真实奖励，而是直接用了 Critic 网络对下一步的预测值 values[t+1] 来代替。

2. 为什么用 TD Target 代替 Gt

在 PPO 或 GAE 的计算中，我们经常看到 rewards[t] + gamma * values[t+1] 这个结构，而不是直接算 Gt*G**t* ，主要有两个原因：

  • 效率更高：计算真实的 Gt 需要等到整个序列结束，把所有未来的奖励都拿齐了才能倒推。而 TD Target 只需要往后看一步就能立刻算出来。
  • 方差更小：真实的 Gt 包含了未来很多步的随机奖励，波动（方差）很大。引入 Critic 的预测值 values[t+1] 相当于加了一个“基准（Baseline）”，能让训练信号更稳定。

3. 它们是如何产生联系的？（GAE 的核心逻辑）

在你之前看到的 GAE（广义优势估计）代码中，它们的关系体现得淋漓尽致： GAE 的核心就是计算每一步的 TD 误差（Delta）： delta_t = rewards[t] + gamma * values[t+1] - values[t]

这里的 rewards[t] + gamma * values[t+1] 就是用来逼近真实回报 Gt*G**t* 的。

  • 如果 Critic 预测得极其完美，那么 values[t+1] 就会非常接近未来真实的折扣回报 Gt+1 ，此时 TD Target 也就几乎等于 Gt 。
  • 正因为 Critic 预测得不完美，所以 GAE 会通过参数 lambda 把多步的 delta 累加起来，以此来不断修正和逼近真实的 Gt 。

总结一下： rewards[t] + gamma * values[t+1] 不等于 Gt​ ，它只是 Gt​ 的一个单步估算版本。真实的 Gt 需要累加未来所有的真实奖励，而这个公式是用“Critic 的预测”偷了个懒，代替了未来繁琐的累加过程。

计算方法

这一步的优势 = 这一步的即时奖励 + 新预测的最终成绩 - 旧预测的最终成绩

  • R_t：在状态 s_t 采取行动后立即获得的奖励
  • V(s_t)：在状态 s_t 预测从此刻到结束能获得的总奖励
  • γ：折现因子（0≤γ≤1），通常接近1
  • V(s_{t+1})：进入新状态后的总奖励预测
λ 取值 含义 等价于
λ = 0 只看当前一步 TD error TD(0)
0 < λ < 1 TD 与 MC 的折中 GAE
λ = 1 看完整轨迹 MC Advantage

A > 0： 👉 这次回答 比 critic 预期的好 👉 应该鼓励 actor 更常这么写

A < 0： 👉 这次回答 比预期的差 👉 应该抑制 actor 再这么写

A ≈ 0： 👉 和预期差不多 👉 别怎么动参数

示例

场景：AI生成句子“我喜欢吃苹果。”

  • 第1步：生成“我”

    • 价值函数（预言家）预测最终奖励：预测分数 = 0.5

  • 第2步：生成“喜欢”

    • 即时奖励（TD）：+0.3（因为“我喜欢”是常见搭配）
    • 价值函数重新预测：预测分数 = 0.8（因为开头不错，提高了最终预期）
    • GAE计算的这一步的优势：0.3（即时奖励）+ 0.8（新预测）- 0.5（旧预测）= +0.6
    • 解读：生成“喜欢”这个词很棒！不仅本身得分高（+0.3），还让预言家对最终结果的预测提升了0.3分，总优势为+0.6。
    • rewards[t]（即时奖励）：对应 +0.3 这是环境（或奖励模型）在你生成“喜欢”这个词后，立刻给出的直接反馈分数。
    • values[t+1]（新预测/下一状态价值）：对应 0.8 这是生成完“喜欢”后，预言家（Critic）站在新的节点上，对未来能拿到的总分的重新预估。
    • values[t]（旧预测/当前状态价值）：对应 0.5 这是在还没生成“喜欢”之前，预言家对这一步的原始预估。

  • 第3步：生成“吃”

    • 即时奖励：+0.2
    • 价值函数重新预测：预测分数 = 0.9
    • 优势：0.2 + 0.9 - 0.8 = +0.3

  • 第4步：生成“苹果”

    • 即时奖励：+0.1
    • 价值函数重新预测：预测分数 = 1.0（句子完整且合理）
    • 优势：0.1 + 1.0 - 0.9 = +0.2

GRPO 的损失计算包含两个层面的“token 级”操作：

  • 重要性采样权重在 Token 级别：GRPO 的核心损失函数使用重要性采样比率 r(θ)，这个比率是在每个 token 上计算的。公式为： r_{i,t}(θ) = π_θ(o_{i,t} | ...) / π_{θ_old}(o_{i,t} | ...) 这意味着模型在优化时，会对生成序列中的每一个 token，都计算新旧策略下出现该 token 的概率比值。
  • 损失聚合在序列级别：虽然权重在 token 级计算，但最终计算损失时，GRPO 采用先序列内平均，再跨序列平均的方式。其公式为： L = - (1/G) * Σ_i [ (1/|o_i|) * Σ_t loss_{i,t} ] 这种“序列级归一化”意味着每个序列对总损失的贡献权重相同，但序列内部的每个 token 对所属序列损失的贡献也相同。

而DAPO考虑了token对损失的影响，从而有效处理长序列中token的影响

一、大模型量化的分类

2. 按量化粒度分类

（1）权重量化（Weight Quantization）

  • 静态权重量化：推理时权重固定为量化值
  • 动态权重量化：根据输入动态调整权重量化参数

（2）激活量化（Activation Quantization）

  • 静态激活量化：使用校准集预先确定激活值量化参数
  • 动态激活量化：推理时实时计算激活值量化参数

（3）权重-激活协同量化

  • 同时量化权重和激活值，实现端到端的低精度推理

3. 按量化位置分类

（1）后训练量化（Post-Training Quantization, PTQ）

原理：在模型训练完成后，通过统计分析确定量化参数

（2）量化感知训练（Quantization-Aware Training, QAT）

原理：在训练过程中模拟量化效应，让模型适应低精度表示

（3）训练时量化（Quantization During Training）

从训练初期就引入量化约束，直接学习低精度表示

二、对称量化和非对称量化

计算公式：

  • S：缩放因子
  • Z：零值
  • x：待量化的浮点数
  • Q：量化后的值

对称量化

  • 反量化：x = Q * S

优势： - 实现简单，计算高效 - 零点是固定的0，减少计算开销 - 广泛硬件支持（如NVIDIA Tensor Core）

非对称量化

假设是 INT8 范围是 q [-128, 127]

  • 反量化：x = (Q - Z) * S

优势： - 更好地利用数值范围 - 适合非对称分布的数据

三、大模型量化的关键技术方法

1. GPTQ（GPT Quantization）

原理：基于Hessian矩阵的逐层最优量化

特点： - 针对Transformer架构优化 - 保持注意力机制的关键特性 - 在LLaMA、GPT等模型上效果显著

2. AWQ（Activation-aware Weight Quantization）

原理：激活感知的权重量化

创新点： - 不依赖反向传播或梯度 - 仅需少量校准数据 - 保持原始模型的准确性

3. SmoothQuant

原理：解决激活值异常值问题

效果： - 实现INT8权重量化和INT8激活量化 - 在LLaMA、OPT等模型上实现接近无损量化

4. LLM.int8()

原理：混合精度分解

特点： - 首次在175B参数模型上实现有效8位量化 - 完全保留FP16精度

5. QuaRot（Quantized Rotary Embeddings）

原理：专门针对RoPE位置的量化

优势： - 针对Transformer位置编码优化 - 保持注意力分数的相对顺序

6. ZeroQuant系列

原理：层级联量化与硬件感知优化

  • 性能：在 RTX 4060 Laptop GPU（Qwen3-0.6B，ShareGPT 数据集，500条）上完成性能验证，推理吞吐由 200.6 tokens/s 提升至 352.3 tokens/s，提升 75%，主要得益于 Batch 合并与 Kernel Launch 开销降低。
